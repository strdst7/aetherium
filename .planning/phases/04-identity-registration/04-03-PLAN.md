Version history rules from CONTEXT.md D-05:
- On PUT, append current state to `versions` array with `version_number`, `sigil_hash`, `updated_at`, `snapshot`
- Increment `version` on main document
- Recompute `sigil_hash` after merge
- `snapshot` is the full identity state excluding system fields (`identity_id`, `sigil_hash`, `version`, `created_at`, `updated_at`, `versions`)

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Client → IdentityController (update) | Untrusted input can attempt to mutate existing identities |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-12 | Tampering | version history array | mitigate | MongoDB `$push` is atomic; no race condition can corrupt the versions array if two updates occur concurrently. Document-level locking is sufficient for v1 scale. |
| T-04-13 | Repudiation | missing update attribution | accept | v1 does not track *who* made an update. Attribution is v2 (ENT-02 with RBAC). The *what* (snapshot) is preserved. |
| T-04-14 | Information Disclosure | version history exposes old fields | accept | By design. Version history is meant to be readable. Access control is v2. |
| T-04-15 | Denial of Service | unbounded versions array | mitigate | No explicit limit in v1. MongoDB document size limit (16MB) is the practical bound. If needed, a future phase can archive old versions to a separate collection. |
| T-04-16 | Elevation of Privilege | no authorization on PUT | accept | Single-tenant v1. All callers can update any identity. RBAC is v2. |
</threat_model>
