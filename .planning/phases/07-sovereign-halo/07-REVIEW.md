## Critical Issues

### CR-01: Council agent "regeneration" appends text instead of regenerating — retry mechanism is a placebo

**File:** `api/src/services/multi-agent-orchestrator.ts:99-103`

**Issue:** The `validateAgentOutput` method's "1 retry" mechanism does not regenerate output. It simply appends a constraint annotation to the existing output and re-validates. This means:

- **Profanity violations are NOT fixed** — the original profanity remains in the output
- **Forbidden content is NOT removed** — the original forbidden text is still present
- **Tone deviations are NOT corrected** — the original tone is unchanged
- **Only symbolic drift can accidentally pass** if the appended constraint text happens to contain an anchor name — but this is coincidental, not intentional

The scope requires "per-agent validation with 1 retry," but the retry path cannot actually remediate any of the validation failures it detects. The output is never regenerated by an LLM — just annotated.

```typescript
// Current broken implementation (lines 99-103):
const tightenedOutput = `${output}\n\n[Constraints: ${violations.join("; ")}]`;
const newReport = await this.sovereignHalo.validate(tightenedOutput, identity);

// Expected: the output should be regenerated via provider, not just annotated
```

**Fix:** The retry should re-invoke the agent (or a generator) to produce a new output that addresses the violations. For example, the agent's `act` method should be called again with the violations included as additional context, or a dedicated provider call should regenerate the output:

```typescript
// Example fix — regenerate via provider with violations as constraints
const regeneratedOutput = await provider.generate({
  model: "gemini-1.5-pro",
  prompt: `Original output: ${output}\n\nFix these issues:\n${violations.join("\n")}\n\nImproved output:`,
  maxTokens: 512,
  temperature: 0.3,
});
// Then validate the regenerated output
const newReport = await this.sovereignHalo.validate(regeneratedOutput.text || output, identity);
```

### CR-02: Empty symbolic anchor value causes false positive detection via `String.includes("")`

**File:** `api/src/services/sovereign-halo.ts:238`

**Issue:** When a `SymbolicAnchor` has no `value` property (or `value` is an empty string), the fallback `|| ""` produces an empty string. `String.includes("")` always returns `true` for any non-null string, so the anchor is always marked as "detected."

```typescript
// Line 238:
const anchorValue = schema.symbolicAnchors.find(a => a.concept === anchor)?.value?.toLowerCase() || "";

// When value is undefined/empty: anchorValue = ""
// outputLower.includes("") is ALWAYS true → anchor always detected
```

This means anchors without configured values (or with empty values) are **never flagged as missing**, giving a false sense of symbolic compliance. Every validation check for such anchors reports `driftScore: 0` and `passed: true`.

**Fix:** Skip anchors with empty values rather than treating them as always present:

```typescript
const anchorObj = schema.symbolicAnchors.find(a => a.concept === anchor);
const anchorValue = anchorObj?.value?.toLowerCase() || "";

// If there's no value, fall back to concept-only matching
if (anchorValue && outputLower.includes(anchorValue)) {
  detectedAnchors.push(anchor);
} else if (outputLower.includes(anchorLower)) {
  detectedAnchors.push(anchor);
} else {
  missingAnchors.push(anchor);
}
```

Or more simply, don't check empty strings:

```typescript
const anchorValue = schema.symbolicAnchors.find(a => a.concept === anchor)?.value?.toLowerCase();
const matchesValue = anchorValue && anchorValue.length > 0 && outputLower.includes(anchorValue);
const matchesConcept = outputLower.includes(anchorLower);

if (matchesConcept || matchesValue) {
  detectedAnchors.push(anchor);
} else {
  missingAnchors.push(anchor);
}
```

## Warnings

### WR-01: Falsy `0` in `getMaxAttempts()` silently overrides explicit zero

**File:** `api/src/services/sovereign-halo.ts:53`

**Issue:** The `||` operator treats `0` as falsy. If a consumer explicitly sets `maxAttempts: 0` (to disable retries), it silently falls back to `MAX_HALO_ATTEMPTS` (3).

```typescript
return this.options.maxAttempts || MAX_HALO_ATTEMPTS;
// maxAttempts: 0 → returns 3 instead of 0
```

**Fix:** Use nullish coalescing (`??`) instead:

```typescript
return this.options.maxAttempts ?? MAX_HALO_ATTEMPTS;
```

### WR-02: Safe fallback message can be empty string when fallback rule has no value

**File:** `api/src/services/sovereign-halo.ts:286-288`

**Issue:** When a fallback rule is configured as `"fallback:"` or `"fallback: "` (empty after colon), the parsed value is an empty string. The `|| ""` fallback does not help because the parsed value already IS `""`. The consumer (orchestrator) would set `responseText` to an empty string, causing the API to return an empty output.

```typescript
// Line 286-288:
const safeFallbackMessage = fallbackRule
  ? fallbackRule.split(":")[1]?.trim() || ""
  : "The generation could not satisfy identity constraints. Please refine your request.";

// If fallbackRule = "fallback:" → fallbackRule.split(":")[1] = "" → .trim() = "" → "" || "" = ""
```

**Fix:** Fall through to the default message when the parsed value is empty or whitespace-only:

```typescript
const DEFAULT_FALLBACK = "The generation could not satisfy identity constraints. Please refine your request.";

const safeFallbackMessage = fallbackRule
  ? (fallbackRule.split(":")[1]?.trim() || DEFAULT_FALLBACK)
  : DEFAULT_FALLBACK;
```

### WR-03: Tone deviation check is a no-op for non-standard tone registers

**File:** `api/src/services/sovereign-halo.ts:148-170`

**Issue:** The tone detection logic only handles `formal`, `authoritative`, `playful`, and `casual` registers. For any other tone (e.g., `somber`, `poetic`, `urgent`, `neutral`), the detected tone remains `neutral` with a deviation of `0.3`. With the default `toneTolerance` of `0.5`, this always passes — effectively making tone deviation checking a no-op for non-standard tones.

```typescript
// Lines 158-170: Only handles 4 specific tone registers
if (expectedTone === "formal" || expectedTone === "authoritative") { ... }
else if (expectedTone === "playful" || expectedTone === "casual") { ... }
// expectedTone === "somber" → falls through to neutral with 0.3 deviation → always passes
```

**Fix:** Either handle all known tone registers, or compute a generic deviation score when the tone is unknown (e.g., treat unknown tones as requiring strict match):

```typescript
// After the existing if/else if block, add:
else {
  // Unknown tone register — treat any deviation from neutral as a failure
  detectedTone = "neutral";
  deviationScore = 0.5;  // At default tolerance, this would need attention
  // Or: treat as strict match requirement
  deviationScore = 1.0;  // Always flag for review
}
```

### WR-04: Inconsistent `maxTokens` fallback between initial and retry generation

**File:** `api/src/services/orchestrator.ts:231,279,409,452`

**Issue:** Initial generation calls pass `req.maxTokens` without a fallback (could be `undefined`), while retry/regeneration calls use `req.maxTokens || 200`. If `maxTokens` is `undefined` or 0, initial and retry generations behave differently.

| Location | Expression | Behavior when undefined |
|---|---|---|
| `processWithTools:231` (initial) | `maxTokens: req.maxTokens` | Passes `undefined` |
| `processWithTools:279` (retry) | `maxTokens: req.maxTokens \|\| 200` | Falls back to 200 |
| `generateAndValidate:409` (initial) | `maxTokens: req.maxTokens` | Passes `undefined` |
| `generateAndValidate:452` (retry) | `maxTokens: req.maxTokens \|\| 200` | Falls back to 200 |

**Fix:** Use consistent fallback across all calls:

```typescript
const maxTokens = req.maxTokens || 200;
// Use `maxTokens` consistently everywhere
```

### WR-05: No type validation for `identity_anchor` in multi-agent controller

**File:** `api/src/controllers/multi-agent.ts:10`

**Issue:** The `identity_anchor` field is only checked for truthiness but not validated as a string. If a non-string value is passed (e.g., number `123`, array `["foo"]`, object `{}`), it would propagate downstream to `IdentityBindingService.resolve()` which may not handle non-string anchors gracefully.

```typescript
// Line 10: Only checks truthiness, not type
if (!identity_anchor || !prompt) { ... }
```

**Fix:** Add explicit type and format validation:

```typescript
if (!identity_anchor || typeof identity_anchor !== "string" || identity_anchor.trim().length === 0) {
  return res.status(400).json({ error: "identity_anchor must be a non-empty string" });
}
if (!prompt || typeof prompt !== "string") {
  return res.status(400).json({ error: "prompt must be a string" });
}
```

### WR-06: No error logging in multi-agent catch block

**File:** `api/src/controllers/multi-agent.ts:15-17`

**Issue:** The catch block sends a 500 response but does not log the error. Silent failures make debugging production issues difficult.

```typescript
} catch (error) {
  res.status(500).json({ error: error instanceof Error ? error.message : "Internal error" });
}
```

**Fix:** Add error logging:

```typescript
} catch (error) {
  console.error("[MultiAgent] Error:", error);
  res.status(500).json({ error: error instanceof Error ? error.message : "Internal error" });
}
```
